# DASgoclient: Ramp `das2go` Dependency to a New Release

This procedure documents how to prepare a new `dasgoclient` ramp-up on top of a specific `das2go` release.

## Example target

```text
das2go release: v04.07.43rc1
release commit: 090a8cde94a7d547907b1d6c3ba6887b3eb71443
```

`das2go` release tags such as `v04.07.43rc1` are project release tags and are not valid Go semantic module versions because of the leading zero in `v04`.

Therefore, `dasgoclient` must pin the exact release commit through the Go pseudo-version generated by `go get`.

## Procedure

Start from an up-to-date `dasgoclient` master branch:

```bash
git checkout master
git pull
git checkout -b ramp-das2go-v04.07.43rc1
```

Update the `das2go` dependency using the exact commit associated with the target release:

```bash
go get github.com/dmwm/das2go@090a8cde94a7d547907b1d6c3ba6887b3eb71443
go mod tidy
```

This updates the existing `github.com/dmwm/das2go` entry in `go.mod` to the corresponding Go pseudo-version and refreshes `go.sum`.

Do **not** keep temporary development overrides such as:

```go
replace github.com/dmwm/das2go => github.com/todor-ivanov/das2go ...
```

or:

```go
replace github.com/dmwm/das2go => ../das2go
```

The production ramp-up must depend only on the upstream `github.com/dmwm/das2go` module.


## Local-tree development build

If `dasgoclient` needs to be built against a local `das2go` checkout before the upstream release ramp, use a temporary Go module replacement.

Assuming the repositories are laid out as:

```text
workspace/
├── dasgoclient/
└── das2go/
```

from the `dasgoclient` directory run:

```bash
go mod edit -replace=github.com/dmwm/das2go=../das2go
go mod tidy
```

This adds the following temporary entry to `go.mod`:

```go
replace github.com/dmwm/das2go => ../das2go
```

Build normally:

```bash
make build
```

Verify that the local tree is being used:

```bash
go list -m -f '{{.Path}} => {{.Replace}}' github.com/dmwm/das2go
```

Before preparing the production ramp-up commit, remove the local override:

```bash
go mod edit -dropreplace=github.com/dmwm/das2go
go mod tidy
```

Then continue with the upstream release pinning procedure below.

## Verify the dependency

Check the resolved module version:

```bash
go list -m -f '{{.Path}} {{.Version}}' github.com/dmwm/das2go
```

For full module metadata:

```bash
go list -m -json github.com/dmwm/das2go
```

Verify that the resolved pseudo-version points to the expected release commit:

```text
090a8cde94a7
```

## Build

Build `dasgoclient` normally:

```bash
make build
```

Verify the resulting client:

```bash
./dasgoclient -version
```

## Regression tests

Run the relevant DAS query regression tests for the changes included in the new `das2go` release.

For `v04.07.43rc1`, this includes the Rucio URL path escaping fix contained in that release.

Use the same queries that were used to validate the fix against the development build before the upstream ramp.

## Expected repository changes

A normal `das2go` dependency ramp should modify only:

```text
go.mod
go.sum
```

No `dasgoclient` source-code change should be necessary unless the new `das2go` release introduces an API change requiring corresponding client changes.

Review the diff before committing:

```bash
git diff -- go.mod go.sum
```

## Commit

Recommended commit message:

```text
Ramping das2go version to v04.07.43rc1
```

Then commit:

```bash
git add go.mod go.sum
git commit -m "Ramping das2go version to v04.07.43rc1"
```


## Distribution to CMS CVMFS

The `das2go` dependency ramp and the `dasgoclient` source release are separate from the procedure used to publish the resulting client into CMS CVMFS.

The documented distribution flow should cover:

```text
dasgoclient change/release
        |
        v
cmsdist update
        |
        v
integration build in cms-ib
        |
        v
validation
        |
        v
promotion/publication to production CVMFS
```

The integration binary should first be validated from:

```text
/cvmfs/cms-ib.cern.ch/sw/x86_64/latest/common/dasgoclient
```

before confirming publication of the corresponding version at:

```text
/cvmfs/cms.cern.ch/common/dasgoclient
```

A successful `cmsdist` build and appearance in `cms-ib` does **not** by itself imply that the production CVMFS copy has already been updated.

### Selecting the correct CMSSW IB branch

Before creating the `cmsdist` branch, determine which CMSSW development IB line should receive the new `dasgoclient` version.

The authoritative source is:

```text
cms-sw/cms-bot/releases.map
```

Look for entries containing:

```text
type=Development
state=IB
prodarch=1
```

A convenient command is:

```bash
curl -s https://raw.githubusercontent.com/cms-sw/cms-bot/master/releases.map \
  | grep 'type=Development;state=IB' \
  | grep 'prodarch=1'
```

Identify the current development CMSSW line from the returned `label=CMSSW_*` entries.

For example:

```text
label=CMSSW_20_1_X
```

Then verify that the corresponding `cmsdist` IB branch exists:

```bash
git ls-remote --heads https://github.com/cms-sw/cmsdist.git \
  'refs/heads/IB/CMSSW_20_1_X/master'
```

The selection procedure is therefore:

```text
1. Check cms-bot/releases.map
        |
2. Find the current:
      type=Development
      state=IB
      prodarch=1
        |
3. Select the appropriate label=CMSSW_* line
        |
4. Verify the matching cmsdist branch exists:
      IB/<CMSSW_VERSION>/master
        |
5. Use that exact branch as the cmsdist PR base
```

Do not permanently hard-code a particular CMSSW version in this procedure. The active development line changes over time.

For the previous ramp-up, the selected line was:

```text
CMSSW_20_1_X
```

and therefore the corresponding PR base was:

```text
cms-sw/cmsdist:IB/CMSSW_20_1_X/master
```

### Creating the corresponding `cmsdist` PR

For the previous `dasgoclient` ramp-up, the PR was opened against the active IB branch:

```text
cms-sw/cmsdist:IB/CMSSW_20_1_X/master
```

from a dedicated branch in the developer fork:

```text
todor-ivanov:IB/CMSSW_20_1_X/master_dasgoclient-v02.04.53
```

The PR changed exactly one file:

```text
dasgoclient.spec
```

The actual version change was:

```diff
-%define dasgoclient_tag v02.04.52
+%define dasgoclient_tag v02.04.53
```

with `version_suffix` left unchanged.

The procedure is:

```bash
git clone git@github.com:<your-user>/cmsdist.git
cd cmsdist

git remote add upstream https://github.com/cms-sw/cmsdist.git
git fetch upstream

git checkout -b IB/CMSSW_20_1_X/master_dasgoclient-v02.04.54 \
    upstream/IB/CMSSW_20_1_X/master
```

Then edit:

```text
dasgoclient.spec
```

and change only the `dasgoclient` tag:

```diff
-%define dasgoclient_tag v02.04.53
+%define dasgoclient_tag v02.04.54
```

The spec already distinguishes between a new upstream `dasgoclient` release and other packaging changes:

```text
# For any other change, increment version_suffix
```

Therefore, for a **new upstream `dasgoclient` tag**, update `dasgoclient_tag`.

Do not bump `version_suffix` merely because a new client release exists.

Review and commit the change:

```bash
git diff -- dasgoclient.spec

git add dasgoclient.spec
git commit -m "Update dasgoclient version to v02.04.54"
git push origin IB/CMSSW_20_1_X/master_dasgoclient-v02.04.54
```

Create the PR with:

```text
base:
cms-sw/cmsdist:IB/CMSSW_20_1_X/master

head:
<your-user>:IB/CMSSW_20_1_X/master_dasgoclient-v02.04.54
```

A suitable PR title is:

```text
Update dasgoclient version to v02.04.54
```

The PR description should briefly explain why the new client is needed and link the relevant `das2go` release/fixes and any related DASMaps changes.

After opening the PR, the CMS build bot starts the integration build/test workflow.

For the previous ramp-up, once testing completed, the bot provided a temporary test installation area under the CMS CI CVMFS space, for example:

```text
/cvmfs/cms-ci.cern.ch/week1/cms-sw/cmsdist/10677/54178/install.sh
```

This can be used to test the PR-built externals before merge.

The complete flow is therefore:

```text
1. Create/tag the new dasgoclient release
        |
2. Checkout current cmsdist IB branch
        |
3. Create dedicated cmsdist branch
        |
4. Change dasgoclient.spec:
      dasgoclient_tag old -> new
        |
5. Commit + push to fork
        |
6. PR against matching cms-sw IB branch
        |
7. cms-bot integration build/tests
        |
8. Optionally test PR build from cms-ci CVMFS area
        |
9. Review/signatures
        |
10. Merge
        |
11. New binary appears in cms-ib
        |
12. Validate cms-ib dasgoclient
        |
13. Production CVMFS publication/promotion
```

The CMSSW IB branch must be chosen deliberately.

The previous ramp targeted:

```text
IB/CMSSW_20_1_X/master
```

but this branch must not be hard-coded permanently. For each new ramp, first determine which active CMSSW IB branch should receive the new client, then branch from that exact upstream branch.

For a future `v02.04.54` ramp, the expected `cmsdist` diff would therefore be:

```diff
%define version_suffix 00
-%define dasgoclient_tag v02.04.53
+%define dasgoclient_tag v02.04.54
```

Nothing related to the `das2go` pseudo-version belongs in `cmsdist`. The selected `das2go` dependency is already encapsulated inside the released `dasgoclient` source/tag.

The exact CMS release/publication step between validated `cms-ib` content and the production:

```text
/cvmfs/cms.cern.ch/common/dasgoclient
```

location is managed outside the `dasgoclient` repository and should be documented or referenced separately.

For reference, the previous update was propagated through:

```text
https://github.com/cms-sw/cmsdist/pull/10677
```

## Notes

Do not manually insert the project release tag into `go.mod`.

Always resolve the exact upstream release commit with `go get`. This lets the Go toolchain generate the correct pseudo-version and avoids manually constructing an invalid or incorrect module version.
